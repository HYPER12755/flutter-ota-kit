# Configuration

`flutter_ota_kit` can be driven **entirely by configuration** — there are no
hard-coded secrets in your committed code. This page is the complete
reference for how the SDK and the CLI resolve every value, where secrets
live, and the exact environment variables per backend.

For setup instructions, see [Getting Started](getting-started.md). For
the CLI commands that read this config, see [CLI Reference](cli-reference.md).

---

## The three config locations

| File / scope | Owned by | Contains | Committed? |
|--------------|----------|----------|------------|
| `.flutter_ota_kit/config.json` (project) | the **CLI** | working state for `migrate` / `deploy` (incl. service-role keys the CLI needs) | **No** — auto git-ignored |
| `~/.flutter_ota_kit/config.json` (global) | the **CLI** | same, but shared across all projects (created by `flutter-ota init --global`) | **No** — outside the repo |
| `.env` (project root) | the **app** | secrets consumed at build time via `--dart-define` | **No** — auto git-ignored |
| `lib/flutter_ota_kit_setup.dart` (generated) | generated by `init` | non-secret defaults, calls `configureX(...)` with `String.fromEnvironment` | **Yes** — safe, no secrets |

`flutter-ota init <backend>` writes the **project** `.flutter_ota_kit/`
and the **project** `.env`, and adds both to `.gitignore`. You normally
only edit `.env`.

Use `flutter-ota init --global` to write the global config instead —
this is shared across all your projects, so the same Supabase / Postgres
credentials are reused.

## Resolution order (env wins)

Every configurable value is resolved in this order:

```
┌──────────────────────────────────────────────────────────┐
│  1. Build-time environment                              │  ← Highest priority
│     (--dart-define, --dart-define-from-file=.env)      │
│                                                          │
│  2. Project config (or global config)                    │
│     (.flutter_ota_kit/config.json)                       │
│                                                          │
│  3. Built-in defaults (e.g. channel=production,           │  ← Lowest priority
│     bucket=bundles, appVersion=1.0.0)                    │
└──────────────────────────────────────────────────────────┘
```

**The environment always wins.** This means you can keep non-secret
defaults in the generated setup file (committed to git), and inject
only the secrets at build time from `.env` (git-ignored). Production
deploys can override via `--dart-define=KEY=value` without touching
the file system.

### What lives where in practice

| Value                          | Where you put it                                          |
|--------------------------------|-----------------------------------------------------------|
| Supabase URL                   | `.env` → `SUPABASE_URL` (or `--dart-define=SUPABASE_URL=...`) |
| Supabase anon key              | `.env` (must be secret — never commit)                   |
| Supabase service-role key      | CLI only — `.flutter_ota_kit/config.json` or env var     |
| `channel: production`         | setup file default; override via `CHANNEL` env var      |
| `appVersion: 1.0.0`           | setup file default; override via `APP_VERSION` env var  |
| Storage bucket name (`bundles`) | setup file default; override via `*_BUCKET` env var  |
| API region (`us-east-1`)      | setup file default; override via `*_REGION` env var     |

## Using `.env` at build / run time

```bash
# dev (hot-reload)
flutter run --dart-define-from-file=.env

# release APK for device / E2E
flutter build apk --release --target-platform android-x64 \
  --dart-define-from-file=.env
```

`--dart-define-from-file=.env` turns each `KEY=VALUE` line in `.env`
into a `--dart-define=KEY=VALUE`. The generated setup reads them with
`String.fromEnvironment('KEY', defaultValue: ...)`. The CLI's
`build` and `deploy` commands also read `.env` through the same
mechanism, so a single `.env` file drives everything.

### `.env` format

```bash
# Comments start with #
# Empty lines are ignored
# Values can be quoted if they contain spaces

SUPABASE_URL=https://xxxx.supabase.co
SUPABASE_ANON_KEY=sb_publishable_xxxx
SUPABASE_BUCKET=bundles
CHANNEL=production
APP_VERSION=1.0.0
SDK_VERSION=1.0.0
```

The parser is intentionally simple — no shell substitution, no
`source` semantics, no multi-line. If you need any of those, use a
real secrets manager and inject the values via `--dart-define`.

## The generated setup file

`init` writes `lib/flutter_ota_kit_setup.dart`. It is **safe to commit**
because it contains only `String.fromEnvironment(...)` reads:

```dart
// generated by `flutter-ota init supabase`
import 'dart:io' show Platform;
import 'package:flutter_ota_kit/flutter_ota_kit.dart';

Future<void> setupFlutterOta() async {
  FlutterPatcher.configureSupabase(SupabaseUpdateConfig(
    supabaseUrl: const String.fromEnvironment('SUPABASE_URL', defaultValue: ''),
    anonKey: const String.fromEnvironment('SUPABASE_ANON_KEY', defaultValue: ''),
    bucket: const String.fromEnvironment('SUPABASE_BUCKET', defaultValue: 'bundles'),
    channel: const String.fromEnvironment('CHANNEL', defaultValue: 'production'),
    platform: Platform.android,
    updateStrategy: UpdateStrategy.appVersion,
    appVersion: const String.fromEnvironment('APP_VERSION', defaultValue: '1.0.0'),
    sdkVersion: const String.fromEnvironment('SDK_VERSION', defaultValue: '1.0.0'),
  ));
  await FlutterPatcher.init(autoApplyUpdates: true);
}
```

Call it once in `main()` after `WidgetsFlutterBinding.ensureInitialized()`
and before `runApp()`:

```dart
Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await setupFlutterOta();
  runApp(const MyApp());
}
```

### Regenerating

If you change backends, run `flutter-ota init <new-backend> --force` to
overwrite the setup file. The CLI keeps your `.env` intact, so you'll
only need to update the new env vars (the CLI will tell you which
ones are missing).

## SDK auto-configuration from environment

You don't strictly need the generated file. `FlutterPatcher.init()`
calls an internal `_autoConfigureFromEnv()` that detects a backend
when none was explicitly configured. It reads the same variables the
setup file uses, so this also works:

```dart
Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await FlutterPatcher.init(autoApplyUpdates: true); // detects SUPABASE_URL etc.
  runApp(const MyApp());
}
```

The generated setup is the recommended path because it makes the
backend explicit and keeps `autoApplyUpdates` on by default.

### Disambiguating between backends

If your `.env` has variables for more than one backend (e.g. you're
migrating from Supabase to PocketBase and forgot to remove
`SUPABASE_URL`), the SDK picks the first match in this order:

1. **Supabase** (if `SUPABASE_URL` is set)
2. **Postgres** (if `POSTGRES_HOST` or `DATABASE_URL` is set)
3. **Cloudflare** (if `CLOUDFLARE_ACCOUNT_ID` is set)
4. **AWS** (if `AWS_BUCKET` is set)
5. **PocketBase** (if `POCKETBASE_URL` is set)

To force a specific backend regardless of what's in `.env`, set
`FLUTTER_OTA_BACKEND`:

```bash
# .env
POCKETBASE_URL=http://localhost:8090
POCKETBASE_ADMIN_EMAIL=admin@local.dev
POCKETBASE_ADMIN_PASSWORD=secret
SUPABASE_URL=https://old-project.supabase.co   # would normally win, but…
FLUTTER_OTA_BACKEND=pocketbase                  # …we override to pick PB
```

`FLUTTER_OTA_BACKEND` is matched case-insensitively. Set it once in
`.env` to make your backend choice explicit and avoid surprise
behavior on stale configs.

## Per-backend environment variables

### Common to all backends

| Variable | Required | Default | Used by | Notes |
|----------|----------|---------|---------|-------|
| `FLUTTER_OTA_BACKEND` | no | unset | SDK init | Force a specific backend (`supabase` / `postgres` / `cloudflare` / `aws` / `pocketbase`). Case-insensitive. |
| `CHANNEL` | no | `production` | SDK + CLI | Bundle channel. Common values: `production`, `staging`, `beta`, `internal`. |
| `APP_VERSION` | no | `1.0.0` | SDK | The app's `versionName`. The backend matches this against each bundle's `target_app_version`. |
| `SDK_VERSION` | no | `1.0.0` | SDK | The flutter_ota_kit version (for analytics; doesn't affect matching). |

### Supabase

| Variable | Required by app | Required by CLI | Default | Notes |
|----------|-----------------|-----------------|---------|-------|
| `SUPABASE_URL` | yes | yes | — | `https://<ref>.supabase.co` |
| `SUPABASE_ANON_KEY` | yes | — | — | publishable key (`sb_publishable_…`) |
| `SUPABASE_BUCKET` | no | no | `bundles` | Storage bucket name |
| `SUPABASE_BASE_PATH` | no | no | `''` | Prefix inside the bucket |
| `SUPABASE_SERVICE_ROLE_KEY` | no | yes (for `migrate`/`deploy`) | — | Never put in `.env`; use shell env or `config.json` |
| `SUPABASE_MANAGEMENT_KEY` | no | optional | — | For `migrate` auto-provisioning |
| `SUPABASE_DATABASE_URL` | no | optional | — | Postgres connection string for `migrate` SQL |

### Postgres

| Variable | Required by app | Required by CLI | Default | Notes |
|----------|-----------------|-----------------|---------|-------|
| `POSTGRES_HOST` | yes | yes | — | |
| `POSTGRES_PORT` | no | no | `5432` | parsed as int |
| `POSTGRES_DB` | no | no | `postgres` | |
| `POSTGRES_USER` | yes | yes | — | |
| `POSTGRES_PASSWORD` | yes | yes | — | |
| `POSTGRES_SERVING_BASE_URL` | yes | yes | — | Where built patches are served from. The SDK can't download bytes directly from a `postgres://` URI; you need an HTTP proxy. |
| `POSTGRES_BASE_PATH` | no | no | `''` | |
| `POSTGRES_SSLMODE` | no | no | `prefer` | `disable` / `prefer` / `require` / `verify-ca` / `verify-full` |

### Cloudflare (D1 + R2)

| Variable | Required by app | Required by CLI | Default | Notes |
|----------|-----------------|-----------------|---------|-------|
| `CLOUDFLARE_ACCOUNT_ID` | yes | yes | — | |
| `CLOUDFLARE_D1_DATABASE_ID` | yes | yes | — | |
| `CLOUDFLARE_API_TOKEN` | yes | yes | — | The Cloudflare API token, not the D1/R2 token |
| `R2_BUCKET` | no | yes | `bundles` | |
| `R2_ACCESS_KEY_ID` | yes | yes | — | R2 S3-compatible access key |
| `R2_SECRET_ACCESS_KEY` | yes | yes | — | R2 S3-compatible secret |
| `R2_BASE_PATH` | no | no | `''` | |
| `R2_ENDPOINT` | no | no | `<account>.r2.cloudflarestorage.com` | Override for S3-compatible stores |

### AWS (S3)

| Variable | Required by app | Required by CLI | Default | Notes |
|----------|-----------------|-----------------|---------|-------|
| `AWS_BUCKET` | yes | yes | — | |
| `AWS_REGION` | yes | yes | — | e.g. `us-east-1` |
| `AWS_ACCESS_KEY_ID` | yes | yes | — | |
| `AWS_SECRET_ACCESS_KEY` | yes | yes | — | |
| `AWS_BASE_PATH` | no | no | `''` | |
| `AWS_ENDPOINT` | no | no | — | For S3-compatible stores (MinIO, R2 via S3 API, etc.) |
| `AWS_SESSION_TOKEN` | no | no | — | For temporary STS credentials |

### PocketBase (self-hosted)

| Variable | Required by app | Required by CLI | Default | Notes |
|----------|-----------------|-----------------|---------|-------|
| `POCKETBASE_URL` | yes | yes | — | `http://localhost:8090` for local dev |
| `POCKETBASE_ADMIN_EMAIL` | yes | yes | — | The PB admin account (not a user account) |
| `POCKETBASE_ADMIN_PASSWORD` | yes | yes | — | Same — the admin password |
| `POCKETBASE_BUNDLES_COLLECTION` | no | no | `bundles` | Name of the PB collection that stores bundle records |
| `POCKETBASE_BUCKET` | no | no | `bundles` | Name of the PB file storage bucket for bundle artifacts |

PocketBase is unique among the 5 backends because **it ships with the
CLI** — `flutter-ota pocketbase install` downloads the PB binary
(~15MB) and `flutter-ota pocketbase serve` starts a local instance
with the schema pre-installed. For production, point
`POCKETBASE_URL` at your own PB instance and skip the CLI's local
server.

## Secrets policy

| Layer | What it contains | Where it lives | Committed? |
|-------|------------------|----------------|------------|
| App secrets (anon key, DB password, R2/AWS keys, PocketBase admin password) | Runtime configuration the app needs at build time | `.env` (or `--dart-define=KEY=value`) | **No** — git-ignored |
| CLI secrets (service-role key, management key, database URL) | Privileged operations the CLI needs (`migrate`, `deploy`) | `.flutter_ota_kit/config.json` (project or global) | **No** — git-ignored |
| Build-time env (any secret) | Override at build time | Shell env, CI secret store | **No** — never logged by flutter-ota tools |
| Non-secret defaults | Things you want committed for reproducibility | `lib/flutter_ota_kit_setup.dart`, `config.json` non-secret fields | **Yes** |

**Rules:**
1. Anything that says "key", "token", "password", or "secret" goes in `.env` or in the shell environment, **never** in the setup file.
2. The CLI never logs the values of secrets. It logs the *names* of the env vars it picked up (e.g. "using POCKETBASE_URL") so you can verify it's reading the right thing without exposing the value.
3. The generated setup file and the non-secret fields of `config.json` are safe to commit and review in PRs.
4. In CI, inject secrets via the CI provider's secret store (GitHub Actions secrets, GitLab CI variables, etc.) and pass them as `--dart-define` to `flutter build` and as env vars to `flutter-ota deploy`.
